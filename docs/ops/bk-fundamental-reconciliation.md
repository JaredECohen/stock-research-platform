# BK financial history reconciliation

The current BNY price symbol must not be reused blindly for historical financial statements. Saved provider checks on September 13, 2026 show the FMP BNY response labeling September 30, 2025 as Q4 while the canonical BK response labels the same bank figures Q3. Fundamentals use canonical `BK` and share-class spelling variants; the independently verified BNY price route remains separate. Both observed statement responses identify the bank's CIK. Their revenue disagreement and the historical reuse of BNY by a BlackRock fund do not prove these rows belong to another issuer.

Canonical-provider reconciliation does not establish comparable bank economics. The [issuer's July 15 release](https://www.sec.gov/Archives/edgar/data/1390777/000139077726000071/ex991_earningsreleasex2q26.htm) exposes mixed revenue definitions and Q2 EPS/share discrepancies in the canonical payload. [Exact numerical evidence](../reviews/2026-09-13-bk-provider-comparability.json) remains an open provider-quality limitation. No inferred revenue, EPS, share, or other economic correction is part of this repair.

Currency placeholders such as `None`, `NULL`, `N/A`, `NAN`, `UNKNOWN`, `XXX`, and `XTS` cannot establish numeric financial coverage or authoritative replacement facts. Incoming and stored history both report those invalid currency identities.

`prepare_bk_repair(bad_fetched_at)` accepts an exact UTC-normalized timestamp and inventories only BK rows bearing that fetch time. It fetches canonical FMP BK history once, to the oldest affected period end, and saves a `FinancialDataRepair` plan. Preparation changes no `FinancialPeriod` rows. The plan contains every original row, every proposed after-image, the provider payload and issues, destination occupants, a unique reserved quarantine namespace, action counts and a SHA-256 digest. All source/value/currency/date/availability identities remain reviewable through `read_bk_repair_plan(plan_id)`.

An affected row can be restored only through a unique provider-explicit fiscal label at the same period end, statement, line and cadence. Unaffected destination occupants are preserved. If two affected rows map to one canonical key, its existing exact-key row can be retained and the duplicate quarantined; ambiguous alternatives are quarantined instead of ranked. A quarantine changes only the ticker to a reserved noncompany `~Q` namespace of 16 characters, preserving the row ID and all original values and dates. The audit retains the original ticker and complete before-image. This is reversible from the saved audit; no row is deleted.

`apply_bk_repair(plan_id, digest)` never calls a provider. It verifies the saved digest, locks the repair and financial rows, and compares the complete current BK/destination state with the saved before-images before any mutation. A changed source, value, timestamp, row set or destination refuses application and requires a new plan. All selected keys move aside before restoration to prevent temporary unique-key collisions. Changes and the applied audit result commit in one transaction; a supplied session keeps commit/rollback ownership. SQLite's deferred BEGIN is handled explicitly before the savepoint so outer rollback remains effective. Applying an already-applied plan returns the saved result without new writes.

Missing plans raise `LookupError`; invalid input or missing canonical data raises `ValueError`; digest, state, fetch and version-fence conflicts raise safe `RuntimeError` messages. No company, memo, snapshot or outcome row is modified. Normal ticker-scoped readers cannot load quarantined rows as BK data; the unscoped PIT availability backfill explicitly excludes `~Q` rows. Coverage counts for normal company targets exclude quarantine namespaces, so any reported physical database total must disclose quarantined rows separately.

The same quarantine mechanism is now generic (`services/fundamental_quarantine.py`, FIX-006): the FMP-primary takeover moves rows that contradict FMP into a fresh `~Q` namespace per ticker-run with a `financial_data_repairs` audit (`kind: fmp_primary_takeover`), fenced per row, and `restore_repair` reverses it. That code reuses this module's `QUARANTINE_PREFIX`, `_snapshot` and `_digest`; the BK plan/apply code is unchanged, and `~Q686e51a5eebc6a` is left as it is. The bk-repair GET reads any audit id; its apply route also applies an unattended `planned` takeover after review. BK itself is stored exactly as FMP reports it (owner decision 2026-09-24): reads carry nonblocking `provider_definition_break` flags for 2026Q1 revenue (gross of 4.454bn interest expense; issuer net 5.409bn) and 2026Q2 diluted EPS (2.43 vs 2.45) and diluted shares (698.164m vs 692.223m), each only while the stored value is within 0.5% of the evidenced provider value, so an FMP correction retires it. The expected re-pull result for BK is zero quarantines.

Tests cover canonical routing, invalid currency sentinels, dry-run preservation, same-date restoration, duplicate/occupied destinations, full before-image fencing, digest tampering, provider-free idempotent application, unrelated row preservation, external-session rollback and global PIT exclusion. Production application requires inspecting the concrete saved plan and its action counts; generating another memo is unnecessary.
